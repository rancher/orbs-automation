# Reference: rancher/frameworks-automation

An inspiration for this project, **not** a project we automate and not a template. We do not assume its choices are right. Reviewed from a local clone and three tracking issues (#250, #248, #244) plus two closed ones (#247, #239). Gathered 2026-10-28; not independently re-verified.

## What it is
* Go only (`github.com/rancher/release-automation`, go 1.26.2), about 11k lines under `internal/`, plus embedded shell scripts in `internal/scripts/*.sh`. One binary, `cmd/reconciler`, with `-mode=cron|dispatch|bump-dep|cascade|validate-config|approve-renovate`.
* No release or install story: every workflow runs `go run ./cmd/reconciler …` after `actions/setup-go`. No goreleaser, no published artifact.
* CI: vet, build, test, `-mode=validate-config`, and an integration job that clones rancher/rancher at a pinned SHA.
* Libraries: `go-github/v66`, `oauth2`, `yaml.v3`, `x/mod`. No shelling out to `gh`; git operations use `exec.Command`.

## Tracking issues
* Generated by the reconciler (`internal/tracker/tracker.go`, `internal/cascade/cascade.go`, `FindOrCreate` in `internal/tracker/ops.go`), no template files. Author is the workflow bot.
* Titles: `[bump:<config>] <dep> <ver> → <leafRepo> <leafBranch>` and `[cascade:<config>] rancher main`. Labels: `bump-op`/`cascade-op`, `config:<name>`, `dep:<name>`, `leaf:<repo>:<branch>`. The version is parsed back out of the title.
* Bodies: human-readable sections (`## Trigger`, `## Targets`, `## Stage N`, `## Status` with `Last reconciled`), a mermaid diagram for cascades, and a hidden versioned block (`<!-- bump-op-state v1 … -->`, `<!-- cascade-op-state v1 … -->`) holding YAML state. The markdown is regenerated from that state every tick.
* Checkboxes are display only. A box is ticked when the PR state is `merged`; labels are used for lookup only.
* In practice: closed examples ran 1.5–3 hours, with one bot comment ("Cascade complete. Closing tracker."). No human edits or comments were seen on any example; the bot comments only when it supersedes an old tracker. Issue churn is high. The final stage's diagram still shows "current" after everything merged, and `current_stage` in the block is zero-based while the text says `3/3`.
* Staleness is visible only by reading `Last reconciled`: #244 (six targets all `pending`, no PRs) sat untouched about twelve days.

## State handling
* Triggers: cron `7,22,37,52 * * * *` (off round minutes because scheduled runs get delayed or dropped), `repository_dispatch` events (`tag-emitted`, `bump-pr-merged`), `workflow_dispatch` for cascades and bumps.
* One global concurrency group (`group: reconciler`, `cancel-in-progress: false`) is the only concurrency control.
* Idempotency: deterministic branch names (`automation/bump-<dep>-<ver>-<branch>`), reuse of an open PR for the head branch, lookup by labels plus title version, `mergeState` that prefers stored values, cascade sources pinned at creation.
* Human edits are not handled: the body is overwritten wholesale; a missing `-->` terminator errors, but a missing block silently yields empty state (the issue is treated as adopted).
* Old trackers are superseded by strict semver "older than", closing old PRs and issue.

## Config and topology
* `dependencies/*.yaml`, one file per sub-DAG (`rancher`, `rancher-chart-webhook`, `rancher-chart-webhook-unrc`, `rancher-chart-remotedialer-proxy`, `-unrc`), each with exactly one leaf. Per repo: `kind: leaf|paired|independent`, `repo`, `token-env`, `deps: [{name, strategy}]`, `branch-template`, `next-tag-strategy`, `post-bundle` hooks, and an inline `version-md` branch-to-minor table (copied into each file).
* Repos repeat across files (`webhook` in both `rancher-chart-webhook` and its `-unrc` twin, which differ only in `next-tag-strategy`). Release strategy (rc vs unrc) is encoded as separate config plus a separate hand-copied workflow.
* Each repo lists its own upstreams; the whole graph is assembled by loading every file. The graph is per branch (e.g. `webhook@release/v0.11` → `chart@dev-v2.15` → `rancher@release/v2.15`).
* A separate `renovateapprove.yaml` holds another policy.

## Auth and workflows
* `GITHUB_TOKEN` (`issues: write`) for trackers; per-repo fine-grained tokens from Vault (OIDC), mapped to `GH_TOKEN_<NAME>`; a PAT (`AUTOMATION_DISPATCH_TOKEN`) for downstream repos to send `repository_dispatch`. The README mentions a GitHub App; the workflows use Vault tokens.
* Downstream repos call a reusable `notify-bump-merged.yaml`. Per-cascade workflows are hand-copied; adding a cascade means editing an input and a shell branch by hand. Actions are pinned by SHA. How downstream repos pin the reusable workflow is unknown (stubs are not in the clone).

## Release semantics
* `next-tag-strategy`: `patch`, `rc`, `unrc`. Tags are not created by the reconciler: humans run each repo's release workflow, and the reconciler only predicts the expected tag. No "stable requires prior RC" rule and no override flag; rc vs stable is chosen by which workflow is dispatched.
* `/releases/latest` excludes prereleases, so a separate tag-polling path exists to cover that gap. Tags must be published GitHub Releases.

## Pain points
* Docs drifted from code (`ARCHITECTURE.md` describes a nonexistent `internal/drift` and a single `dependencies.yaml`). A stub `pass3`. Dead `chart-bump` strategy and near-duplicate `unrc-*` configs. Unpaginated release listing (one page of 100) and PR listing (one page of 50). High token fan-out (11 per-repo Vault tokens, edited per new repo). A stale tracker has no trigger to refresh it.

## Ideas worth taking and avoiding
* **Take:** hidden versioned state block with markdown rendered from it; additive-only schema; stable identity from labels plus fields; deterministic branch names; off-peak cron minutes; SHA-pinned actions; fixture-driven tests (`testdata/runcascade/*`); credential-free `validate-config`; pinning cascade sources at creation.
* **Avoid or change:** overwriting the whole body, a missing block treated as empty, ambiguous checkboxes, a global lock, no published binaries, per-goal config files that repeat repos, release strategy mixed into topology, version identity only in the title, unpaginated listings, undefined prerelease handling, drifting docs.

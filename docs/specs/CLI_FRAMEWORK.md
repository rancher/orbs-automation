# CLI Framework

**Status:** implemented, except what [Not built yet](#not-built-yet) lists.

How `gero` is built as a CLI: framework, command tree, global flags, context gating and exit codes. Product design is in [ARCHITECTURE_DESIGN](../ARCHITECTURE_DESIGN.md). Settings and their sources are in [CLI_CONFIG](CLI_CONFIG.md).

## 1. Framework

**cobra**, with a custom CLI-config loader ([CLI_CONFIG](CLI_CONFIG.md)). No viper.

| Option | Verdict |
|---|---|
| **cobra** + custom loader | **Chosen.** The same framework as `gh`, so command idioms match (VISION) and the ecosystem (completions, docs generation, `go-gh` examples) is mature. |
| cobra + viper | Not chosen, kept as the fallback. Viper brings a large transitive tree. It ignores unknown keys by default, so a typo in a user file fails silently. It has a global singleton, case-insensitive keys, type coercion, and quirks when a config value meets a flag default. Our CLI config is a handful of flat keys, which does not earn that cost. |
| urfave/cli v3 | Not chosen. Lighter, with per-flag env sources, but a smaller ecosystem and less aligned with `gh`. |
| stdlib `flag` | Not chosen. Nested subcommands, help and completions would be hand-rolled. |

**Viper adoption trigger.** Revisit only if CLI config grows past roughly ten keys, needs nested or per-command sections, needs more than one file format, or needs watching or remote sources. The swap stays local because everything downstream reads one resolved `Settings` struct from `internal/gero/clicfg`.

**Structure.** The root command and global flags live in `cmd/`, which imports only cobra, the standard library, `cmd/...`, `internal/cli/...`, `internal/gero/clicfg` and `internal/gero/errs` (lint-enforced, see Enforcement in [PROJECT_LAYOUT](PROJECT_LAYOUT.md)). All cobra code stays in `cmd/`: the command tree, help text, flags, annotations and gating. A command's `RunE` there is glue only: it turns args, flags and the environment into plain values, calls the command's package `internal/cli/<cmd>/` (plain functions, no cobra), writes the output and returns the error. A command that does one action, or chains several, calls them as tasks in `internal/task/` ([PROJECT_LAYOUT](PROJECT_LAYOUT.md#tasks-single-actions-that-compose)). That package builds dependencies from `Settings` and calls into domain packages in `internal/`, so the logic is testable without cobra, and `cmd/` needs only wiring tests.

## 2. Command tree and global flags

Human-run commands are noun-verb chains, like `gh` (real parent commands such as `gero config validate`). CI-only commands are prefixed `ci:` and listed under a cobra help group, modeled on `ob-charts-tool`. **Context** is CI-only (gated by the `gero/context` annotation) or either ([execution contexts](../IMPLEMENTATION.md#execution-contexts)). A command built for an engineer's clone is not gated by the annotation, and `gero repl` refuses CI itself. A third value, `workstation-only`, marks a command that must not run in CI or inside `gero repl` (the first is `gero doctor self-update`): the same `PersistentPreRunE` refuses it there (`cigate.RequireWorkstation`), and the tree hides it from help and completion when it is built in either (`hideWorkstationOnly`). Each REPL line builds a fresh tree after `GERO_REPL` is set, so the hiding holds there too. The refusal is what enforces it; the hiding only keeps it out of sight, and both read environment variables that a person can set.

| Command | Context | Notes |
|---|---|---|
| `gero config validate` | either | Runs without credentials. Prints a summary and each warning; with `-v` it also lists the warnings a document acknowledges, with their reasons ([APP_CONFIG](APP_CONFIG.md)) |
| `gero config show` | either | Read-only; the resolved CLI settings (flags, `GERO_*`, the user file, defaults) with the layer each value came from; `--json` and `--output env` supported. The application config with defaults applied (`--resolved`) is not built ([APP_CONFIG](APP_CONFIG.md)) |
| `gero config resolve repos [name|owner/name|.]` | either | Read-only; local path of each central-config repo and how it was found ([WORKSPACE](WORKSPACE.md)); `--json` supported. Prints its table before exiting 1 when a repo is unresolved or ambiguous |
| `gero config resolve graph` | either | Read-only; the whole application config as D2 source on stdout (`--json` is refused): projects as nodes, holdings as nodes between producer and holder, stewardship and the final destination as classes, release lines as edge labels ([CONFIG_GRAPH](CONFIG_GRAPH.md)) |
| `gero cd <name\|owner/name>` | either (built for workstations) | Read-only; prints the local clone of a project, found only by the user file (`repos.paths`, else `repos.search`), for a shell function to `cd` into: a program cannot change its parent's directory. The project is always named, never implied. Exits 1 when the project is unknown or has no unique clone ([WORKSPACE](WORKSPACE.md)) |
| `gero shell init <bash\|zsh\|fish\|powershell>` | either (built for workstations) | Read-only; prints the completion script and the `gero` function that makes `gero cd` change directory ([SHELL_SETUP](SHELL_SETUP.md)) |
| `gero shell install`, `gero shell uninstall` | either (built for workstations) | Writes the user's shell profile, inside one marked block, after asking (`--yes` to approve, `--shell`, `--profile`); honors `--dry-run` ([SHELL_SETUP](SHELL_SETUP.md)) |
| `gero init` | workstation | Writes the user file from `--github-user`, `--fork`, `--upstream`, `--branch-prefix`, `--central-config-dir`, `--search` (repeatable or comma-separated) and `--clone-root`, asking on a terminal for any not given. An empty answer skips a question and leaves its key out; without a terminal nothing is asked and what has no flag is skipped. Before the two path questions it says that `repos.search` finds clones that exist and `repos.cloneRoot` is where `gero repo clone` puts new ones, and that the root is scanned too, so it need not be in the search list. Refuses an existing file unless `--force`, which also replaces one that cannot be loaded; honors `--dry-run`. The paths are checked as every command checks them. Not for the REPL, and refuses in CI unless `GERO_CONFIG` names the file. The file starts with the schema comment ([CLI_CONFIG](CLI_CONFIG.md#the-file)) |
| `gero repl` | workstation | An interactive prompt that runs this table's commands a line at a time, with `pwd`, `ls`, `clear`, `shell` and `exit` of its own, and `cd` changing the REPL's own directory. Needs a TTY; refuses in CI ([REPL](REPL.md)) |
| `gero auth status [--hostname host]` | either | Read-only; the host and token source gero would use (`GH_TOKEN`, `GITHUB_TOKEN`, gh config, gh keyring) and the login GitHub reports for the token; the token is never printed. Prints its result before exiting 1 when GitHub rejects the token. `--json` supported |
| `gero doctor [check...]` | either (built for workstations) | Read-only; checks the workstation setup and says how to fix what is not. Offline unless `--online`; `--json`, `--list-checks` and `--strict` ([DOCTOR](DOCTOR.md)) |
| `gero doctor self-update` | workstation-only | Replaces the running binary with the newest release after verifying its Sigstore signatures; asks once, `--yes`, `--check`, `--dry-run`. Refused and hidden in CI and in `gero repl` ([SELF_UPDATE](SELF_UPDATE.md)) |
| `gero version` | either | Read-only; prints the build version, commit and date, the same text as `--version`. `--json` supported |
| `gero lines resolve [line...]` | either | Read-only, config and clock only, never the network. The release-line map ([LINES_RESOLVE](LINES_RESOLVE.md)): each Rancher line, newest first, with its phase, dates and Kubernetes range, the hub project's branch for it, what takes from the hub and what it ships to, the other projects on the line with their connections, and the gaps. `--hub`, `--phase`, `--json` supported |
| `gero semver check [tag]` | either | Read-only; port of the shared `check-semver` script. Takes a string (argument or `GITHUB_REF_NAME`) and never opens a repository. Emits env-style output |
| `gero repo list` | either | Read-only, never touches the network, and exits 0 when something is not cloned: which Projects of the central config have a clone on this machine. Three lists: **Cloned** (slug and path, only where the directory exists), **Not cloned** (slugs), and **Ambiguous** (a Project with several equally good clones, with the paths). A `repos.paths` entry whose directory is missing is not cloned. A Project outside the organization (`external`) is listed only when it is cloned, since `gero repo clone --all` leaves it out. Clones are found as everywhere else ([WORKSPACE](WORKSPACE.md)); it reports what is on disk, where `gero config resolve repos` reports how the config resolves each repository and from which source, and exits 1 when one does not resolve. `--json` supported |
| `gero repo info [name|owner/name]` | either | Read-only and **never touches the network**; a Project's config entry with defaults applied (which team manages it, shown as unspecified when it names none, whether the active team owns it, and whether it is `shared`; release policy, and the line to series to branch mapping), and its local clone: where it is, how it was found, its branch, HEAD and whether the tree is dirty. It may also show the remote refs the clone last fetched, labeled "as of last fetch". Defaults to the repository you are in. A missing clone leaves the rest of the report. There is no `--offline`: the command has no online mode. `--json` supported |
| `gero repo status [name|owner/name]` | either | Read-only, reads the host; one Project at a time, never all. The live view of a Project's releases, in sections that each answer one question ([REPO_STATUS](REPO_STATUS.md)): Releases (per release line the newest tags, the branch head, a named state and the tags it could have next), Local clone (the commits since the newest tag and whether the clone is behind or ahead), and Sources and Consumers (what the projects that ship to this one, and the ones it ships to, hold of each release), the last two only for a project that has them and skippable with `--no-sources` and `--no-consumers`. A failed read of the host or a missing clone leaves the rest of the report; the report is printed before exit 1 when the host could not be read, and a missing clone is not a failure (it only leaves out the commit counts and the comparison). Does not read tracking issues. `--json` supported |
| `gero repo images exist [name|owner/name] <tag>` | either | Read-only, needs the network; port of `validate_image_exists`. Checks that each image a Project publishes exists in the required registries ([IMAGES_EXIST](IMAGES_EXIST.md)). Prints its rows before exiting 1 when an image is missing or unreachable. `--json` supported |
| `gero repo build-tags` | either | Read-only; port of the shared `branch-tags.sh` script: the rolling, fixed and previous fixed tags of a build of this branch's head. Emits env-style output. `current-tags` is an alias |
| `gero ship [project] [tag|line]` | workstation | Writes; honors `--dry-run`. Downstream PRs: resolves the tag, checks the state of each consumer branch the release goes to (`--line` for one), then edits, commits, pushes and opens a PR for each, superseding an older one ([PUSH_TO_REPO](PUSH_TO_REPO.md)). Works in the engineer's own clone of the consumer and asks once before it pushes. A consumer with several routes for the producer is chosen by tag or by line, and a Rancher line as the argument means `--line` ([PUSH_TO_REPO](PUSH_TO_REPO.md#choosing-the-route-when-a-consumer-takes-several-streams)). A producer the active team does not own is refused, except with `--to` naming a consumer it owns or one that is `shared` ([PUSH_TO_REPO](PUSH_TO_REPO.md#shipping-another-teams-release)). The flags (`--line`, `--to`, `--yes`, `--push-to`, `--refresh`, `--no-push`, `--prerelease`, `--allow-downgrade`, `--preview`) are in [PUSH_TO_REPO](PUSH_TO_REPO.md) and `gero ship --help`. `--json` supported |
| `gero repo branch [project] <line> <name>` | workstation | Writes the local clone only, so it asks nothing; honors `--dry-run`, `--json` supported. Makes a branch off the upstream branch of a release line and leaves the checkout alone; `--switch` moves onto it ([TASK_COMMANDS](TASK_COMMANDS.md)) |
| `gero repo tag [project] <line> [tag]` | either | Makes a lightweight tag in the clone, so it asks nothing; `--push` sends it to the upstream and asks once (`--yes` or `GERO_NON_INTERACTIVE` skips it). Honors `--dry-run`, `--json` supported (a push needs `--yes`). The tag is on the head of the upstream branch of a release line, chosen from the line's newest when not named (`--stable`, `--minor`, `--major`), never moving one ([TASK_COMMANDS](TASK_COMMANDS.md#gero-repo-tag-project-line-tag)) |
| `gero repo clone [project...] [--all] [--into <dir>]` | workstation | Writes new clones, so it asks nothing; honors `--dry-run`, `--json` supported. Clones each named Project, or with `--all` every Project the active team owns (its `managedBy` is the `team` setting) and that is not `external` (an external one needs its name), into `<root>/<name>`, `<name>` being the repository's name and not the Project's. The root is `--into`, then env `GERO_REPOS_CLONE_ROOT`, then `repos.cloneRoot`, and a `repos.paths` entry for the slug beats it ([CLI_CONFIG](CLI_CONFIG.md)); with none set the command fails naming the three. Uses SSH. With a `fork` and `githubUser` configured it clones the fork (a repository of the same name under `githubUser`) as the fork remote and adds the upstream; when that fork does not exist on the host it clones the upstream alone, under the upstream remote's name, and says so. A clone already there with the right remote is skipped and reported; a non-empty directory that is something else fails that Project only, the rest go on, and the exit is 1 if any failed. The Projects come from the central config, found as every command finds it: a local directory when one is named, else the central bundle of the `gero` release, so a fresh workstation needs no checkout ([CLI_CONFIG](CLI_CONFIG.md#locating-the-central-application-config), [CENTRAL_BUNDLE](CENTRAL_BUNDLE.md)). Runs the `git` binary, not go-git, so the user's SSH setup is used ([GITHUB_ACCESS](GITHUB_ACCESS.md)) |
| `gero ci:ship` **(not built)** | CI-only | The bump loop of `gero ship` as the bot, for one release event, over the checkouts the workflow provides ([CI_SHIP](CI_SHIP.md)) |
| `gero workflows sync` | either | Writes; honors `--dry-run`. Acts on a repo only when a workflow config is found in it at the defined branch and path, and then only when the active team owns the project ([CLI_CONFIG](CLI_CONFIG.md)) |
| `gero workflows verify` | either | Drift check; exits 3 when a copy has drifted. Gated as `sync` is |
| `gero ci:reconcile` | CI-only | Runs from a cron and from `repository_dispatch`; the only reconciler entry point. Named with the group prefix, listed under the CI-only help group |
| `gero dashboard` | either | Moonshot; the name may become `triage` |

A noun names the thing a command operates on. `gero repo` is for commands that read a repository (its refs, HEAD, tags), so the project arguments below and the upstream and clone paths in [CLI_CONFIG](CLI_CONFIG.md) apply to everything under it. `gero semver` works on version strings and never opens a repository. The noun names the domain, not the implementation: `semver check` is the lenient script port (any text, one leading `v` stripped). Later verbs such as `compare` or `bump` may use a strict SemVer parser, which needs its own entry in [DEPENDENCY_POLICY](DEPENDENCY_POLICY.md); they get their own verbs and must not change what `check` accepts.

**Project arguments.** Wherever a command takes a project, it takes the config `name`, the repository's `owner/name` slug or one of the project's aliases, case-insensitive, and `.` for the project whose repository the working directory is in. Where the project is optional, leaving it out means the same as `.`; the one exception is a command where leaving it out already means all projects (`gero config resolve repos`), which takes `.` explicitly. `gero cd` is the other exception: it always needs a name, and refuses `.`, since the directory you are in is where `.` would go. A command that takes a project and a release reads a lone argument as the release, with the project from the working directory: always for `gero repo images exist`, which needs a tag, and for `gero ship` when the argument looks like a version or a release line (`v0.5.3`, `v2.15`), since no project is named like that. One lookup does all of this for every command (`Workspace.Project`, [WORKSPACE](WORKSPACE.md)), so no command spells its own; outside a project the error says the working directory is not one. Inside `gero repl` the working directory is the REPL's, which `cd <project>` moves, so a command with no project named acts on the project the user last changed into ([REPL](REPL.md#working-directory-is-the-session-state)).

Global (persistent) flags:

| Flag | Meaning |
|---|---|
| `--central-config-dir` | Where the central config is ([CLI_CONFIG](CLI_CONFIG.md)); env `GERO_CENTRAL_CONFIG_DIR` |
| `--config-source auto\|bundle\|dir` | Where the central config comes from, a local directory or the release bundle ([CLI_CONFIG](CLI_CONFIG.md#locating-the-central-application-config)); env `GERO_CONFIG_SOURCE` |
| `--bundle-channel auto\|stable\|prerelease` | Which releases the bundle may come from ([CENTRAL_BUNDLE](CENTRAL_BUNDLE.md)); env `GERO_BUNDLE_CHANNEL` |
| `--bundle-file <path>` | One bundle file, downloaded by hand, as the central config; env `GERO_BUNDLE_FILE` |
| `--upstream <remote>` | The remote treated as the real source; env `GERO_UPSTREAM` ([CLI_CONFIG](CLI_CONFIG.md)) |
| `--output text\|json\|env` | The output format; env `GERO_OUTPUT`. `--json` is shorthand for `--output json` |
| `--dry-run` | Commands that write (to disk, git or GitHub) compute and print what they would do, and change nothing: no branch is pushed and no PR is opened. Read-only commands accept and ignore it. Env `GERO_DRY_RUN`; not a user-file key, so a file cannot turn it on for every run. Default is off, with `gero workflows verify` as the explicit check mode. |
| `--non-interactive`, `--yes` | On the commands that write (`gero ship`, `gero repo tag`; `gero shell install` has `--yes`; `gero init` has `--force` for an existing file and never confirms), not global: never prompt (env `GERO_NON_INTERACTIVE`, which any command reads), and answer yes to the one confirmation a write command asks before it starts ([EXECUTION_CONTEXT](EXECUTION_CONTEXT.md#write-command-contract)). Without it, a write command with no TTY fails before writing |
| `--json` | Machine output ([CLI_OUTPUT](CLI_OUTPUT.md)); shorthand for `--output json`. `--output env` prints `KEY=value` lines for `$GITHUB_OUTPUT` and `$GITHUB_ENV` |
| `-v`, `--verbose` | Raises log level ([CLI_OUTPUT](CLI_OUTPUT.md)): `-v` is `info`, `-vv` is `debug`. Wins over `GERO_LOG` |
| `--color auto\|always\|never` | When output is styled ([CLI_OUTPUT](CLI_OUTPUT.md#terminal-capabilities)). `auto` (default) follows `NO_COLOR`, `CLICOLOR_FORCE`, `TERM` and whether stdout is a TTY. `always` and `never` decide it, and beat those variables |
| `--no-color` | Shorthand for `--color never` |
| `--version` | Prints the version and exits, with no shorthand. Root only, not persistent. The value comes from `cmd/version`, set by GoReleaser through `-ldflags -X` (`.goreleaser.yaml`); a plain `go build` prints `dev`. `gero version` is the primary form and prints the same text |

**Network policy.** A command that needs the network to do its job reads it, and does not ask first: an opt-in flag on every read would make the commands tedious to use. `GERO_OFFLINE=true` makes the central config bundle come from the cache only ([CLI_CONFIG](CLI_CONFIG.md)). `gero repo info` is local-only by design, with no online mode to opt out of, and `gero repo status` is its networked counterpart. Reads that a public repository allows are made anonymously, and a token is sent only when the host asks for one. `gero doctor` is the exception, offline by default with `--online`, because it checks the workstation itself ([DOCTOR](DOCTOR.md)).

Per-command flags are defined with their command and follow `--kebab-case`.

## 3. Execution-context gating

A command declares its context with a cobra annotation, for example `gero/context: ci-only`. Each CI-only command also joins the cobra help group `ci` ("CI-Only Commands:", defined in `cmd/groups`), so `gero --help` lists them apart from the human-run noun-verb commands. One shared `PersistentPreRunE` enforces it: CI-only commands require the CI context (`GITHUB_ACTIONS=true`, `CI=true` or `GERO_CONTEXT=ci`, so one can be run locally to debug) and a token, and otherwise fail fast with a clear error. The annotation also drives a marker in `--help`, so gating is declared once per command and never reimplemented inside `RunE`.

Commands that run in both contexts behave the same in each, except for who acts and where inputs come from. That, and the rules for commands that write, are in [EXECUTION_CONTEXT](EXECUTION_CONTEXT.md).

## 4. Exit codes

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | Runtime error (I/O, GitHub, unexpected) |
| 2 | Usage or validation error (bad flag, invalid config) |
| 3 | `gero workflows verify` found a copy that has drifted |

One helper maps errors to codes so commands return errors and never call `os.Exit`.

## Not built yet

* `gero workflows sync`, `gero workflows verify` and `gero ci:reconcile` are stubs that return `errs.NotImplemented`. `gero ci:ship` and `gero dashboard` are not registered. The remaining steps of `ship` are [use cases](TASK_COMMANDS.md#use-cases-not-yet-commands) without command names, and get one only if someone asks.
* The exit-code helper. Until it exists, a usage or validation error exits 1, not 2.
* `--json` for `config validate`, and `--output env` for `auth status`.

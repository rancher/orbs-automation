# Dependency Policy

**Status:** implemented. The YAML library is `go.yaml.in/yaml/v3`, moving to v4 once it is stable.

* **Standard library first.** Fewer dependencies means a smaller supply-chain surface and less to audit.
* A new dependency needs an entry here saying what the standard library would cost us. It is enforced by a `depguard` allow-list in `.golangci.yml`, so an unlisted import fails lint. Narrower rules there keep each module behind one package ([PROJECT_LAYOUT](PROJECT_LAYOUT.md)).
* **Network reads that are not modules:** the Go release list (`https://go.dev/dl/?mode=json`), read anonymously by `internal/platform/goreleases` to name the newest patch of a Go minor, and cached for a day. It is a plain HTTP read of JSON with the standard library.
* Approved now:

| Module | For |
|---|---|
| `github.com/spf13/cobra` | Command tree, flags, help, completions ([CLI_FRAMEWORK](CLI_FRAMEWORK.md)) |
| `github.com/cli/go-gh/v2` | **Only `pkg/auth`**: token and host resolution, bridging off the user's `gh` setup ([GITHUB_ACCESS](GITHUB_ACCESS.md)). Doing it by hand would mean re-implementing the env var order, the `hosts.yml` reading and the keyring fallback through `gh auth token`. `pkg/api` is not approved: it brings a GraphQL library, `httpretty` and a timezone library, and is added only if GraphQL beats REST for a real need. |
| `github.com/google/go-github` | Typed REST, authenticated with its own `WithAuthToken` ([GITHUB_ACCESS](GITHUB_ACCESS.md)) |
| `github.com/go-git/go-git` | **Only in `internal/platform/git/repo`.** Reading a local repository: the current ref, the abbreviated commit and tags by date ([GITHUB_ACCESS](GITHUB_ACCESS.md)). It needs no `git` binary for that and starts no subprocess. Everything that touches a working tree runs the `git` binary through `gitcli`, so this is the smaller of the two. Costs a larger transitive tree than `os/exec`, accepted for the reads. |
| `github.com/mallardduck/ghreleases` | **In use, only in `internal/gero/assetfetch`**, besides the Sigstore verifier in `internal/gero/releasesign` below. Finding a GitHub release, choosing the newest one (stable, or any when asked), downloading its assets and verifying them against the published checksum and, through a verifier, its signatures ([CENTRAL_BUNDLE](CENTRAL_BUNDLE.md)). By hand that is release lookup, stable-versus-prerelease selection, redirects, streaming downloads and checksum parsing and comparison, which is security-relevant code we would rather not write twice. It is our own module, so we can fix it at the source. A `depguard` rule keeps it behind the one package that downloads and verifies release assets. |
| `github.com/mallardduck/binup` | **In use, only in `internal/gero/selfupdate`.** `gero doctor self-update`: finding the newest release, comparing versions, refusing a binary a package manager owns or the user cannot write, and swapping the running executable atomically with a rollback ([SELF_UPDATE](SELF_UPDATE.md)). By hand that is the swap, which differs by operating system, and the guards around it, which are easy to get wrong in the direction of overwriting a Homebrew install. It is our own module, over `ghreleases` and `minio/selfupdate`. A depguard rule keeps it behind that one package. It reaches `ghreleases` through its own `github` source; `internal/gero/assetfetch` remains the only package that imports `ghreleases` directly for the central bundle, and the Sigstore verifier is made in `internal/gero/releasesign`. |
| `github.com/mallardduck/ghreleases/sigstore` | **In use, only in `internal/gero/releasesign`**, for self-update and for the central bundle fetch. The verifier that authenticates a release against a keyless Sigstore bundle signed by a pinned identity: the release workflow of this repository, on a version tag. It is the highest level `binup` offers, and a checksum alone is not authenticity, since whoever can replace the release can replace `checksums.txt` too. The standard library has no Sigstore; this is `sigstore-go` behind a small adapter. It is by far the largest dependency, many modules, accepted because self-update is the place a wrong answer installs attacker code on an engineer's workstation, and the bundle is the config every command then acts on. Its own module declares a Go version above `binup`'s. |
| `go.yaml.in/yaml/v3` | **In use.** The one YAML library, for the config engine (`internal/platform/config`, which also reads the user file for `internal/gero/clicfg`), and the versioned config API (`internal/apis`, which decodes its own documents so a version's types and their YAML form change together). Chosen because it supports strict decoding (`KnownFields(true)`, so an unknown key is an error, or for the user file a warning that names the line) and multi-document streams (`yaml.NewDecoder`), and it was already in the tree through testify. Stay on v3 until `go.yaml.in/yaml/v4` has a stable release, then migrate. Until then it is importable only from `internal/platform/config`, `internal/apis` and `internal/platform/yamledit` (lint-enforced), so the migration touches known files. `internal/platform/yamledit` changes one value of a downstream file in place, which needs the node positions to splice into the original bytes, and keeps that out of the config engine, and the engine's tests pin the behavior that must not change: unknown keys, malformed input, empty files, errors naming the file. |
| `golang.org/x/mod/modfile` | **In use, only in `internal/platform/gomodedit`.** Reading and replacing the version of a module in a `go.mod`, for a Holding in the `gomod` format. The standard library has no `go.mod` parser, and a line scanner would have to get the grammar right itself: `require` as a line or a block, quoted paths, comments and `// indirect`, the other directives that name a module. It is the parser the Go team maintains, already in the module graph as an indirect dependency (so no new supply-chain surface), and it gives the position of each `require` line, so the edit changes the version text and nothing else. Only its `modfile` package is allowed, and a depguard rule keeps it out of everything else. |
| `golang.org/x/net/html` | **In use, only in `internal/lifecycle`.** Reading Rancher's lifecycle dates from the SUSE lifecycle page, which is HTML. The standard library has no HTML parser, and reading a page that is built from nested tables with regular expressions would break on the first change to the markup. It is the HTML tokenizer and parser the Go project maintains, with nothing beyond the standard library and its own `atom` package behind it, and a depguard rule keeps it out of everything else. |
| `charm.land/lipgloss/v2` | **In use, only in `internal/ui/style`.** Styles for human output (color, bold, dim) and the REPL prompt, downsampled to the terminal's color profile. By hand that is a table of escape codes per profile, the downgrade from truecolor to 256 to 16 colors, and the width of text with wide characters. Why it and not the alternatives is in [CLI_OUTPUT](CLI_OUTPUT.md#why-these-libraries). v2 `Render` always returns full escapes, so what is written is downsampled by our own `Terminal` value, never by lipgloss's own detection of stdout. |
| `github.com/ergochat/readline` | **In use, only in `internal/ui/editor`.** The REPL's line editor: history in a file, Ctrl-R, line editing and completion. By hand it is raw-mode input, redraw on wrap and resize, and history, a few thousand lines to get wrong across terminals. The maintained fork of `chzyer/readline`, with a small tree ([REPL](REPL.md)). |
| `golang.org/x/term` | **In use, only in `internal/cli/termfacts`.** Whether stdin and stdout are terminals, and the width of stdout. The standard library cannot say: `os.File.Stat` reports a character device, which is also true of `/dev/null`, so `gero repl </dev/null` passed for a TTY. `x/term` asks the terminal driver (`IsTerminal`, `GetSize`). The editor and the styling are behind their own packages ([REPL](REPL.md), [CLI_OUTPUT](CLI_OUTPUT.md)). |
| `github.com/invopop/jsonschema` | **Developer tool, only in `tools/genschema`.** Derives the JSON Schemas of the config files from the Go types, for editors ([APP_CONFIG](APP_CONFIG.md)). It reads the `yaml` tags the decoder reads, refuses extra keys as strict decoding does, and turns Go comments into descriptions. By hand that is a reflector, a draft 2020-12 schema model and comment extraction. It brings `pb33f/ordered-map` and two small modules, and the `gero` binary does not link it: a depguard rule keeps it out of everything but the tool. `google/jsonschema-go` was read and does not fit: it names fields from `json` tags only and has no hook for enums. |
| `github.com/stretchr/testify` | **Tests only, in use.** `require` and `assert` for the strong test-first workflow ([TESTING](TESTING.md)); the standard library makes table tests and diffs of structs noisy. |
| `github.com/spf13/pflag` | **Tests only.** Walking the flags of every command, in `cmd`'s tests. Production code reaches flags through cobra. |
| `go.uber.org/mock` | **Tests only, in use** (`mockgen` is pinned as a `tool` in `go.mod`). `mockgen`-generated mocks for interfaces at package seams (today the `Repository` of `internal/cli/branchtags`); most tests use hand-written fakes and fake transports, so tests drive behavior without network access. |

* **Developer tools that are not imported stay out of `go.mod`.** `gremlins` (mutation testing, [TESTING](TESTING.md)) is optional and installed globally by whoever wants it, because its own dependencies do not fit this policy. Tools pinned with a `tool` directive, like `mockgen`, are fine when their dependencies are acceptable.
* Test-only modules are imported from `_test.go` files and from generated mock packages, never from production code. The `depguard` `main` rule excludes `$test`, so they stay out of the production allow-list. Use them where they help, not by default: plain `testing` is fine for a simple case.
* **Running another program (`os/exec`)** is for the `git` binary, where the engineer's own SSH agent, credential helpers and signing setup are needed, and for `gero doctor` asking what the `gh` and `git` binaries would do ([GITHUB_ACCESS](GITHUB_ACCESS.md)). It is not a runtime fallback for go-git.
  * `os/exec` is importable only from `internal/platform/execx`, the one place `gero` starts another program. Its contract (an allow list of binaries, an argument vector never a shell string, a scrubbed environment so `GH_TOKEN` does not reach a child, raw output and exit code) is in the package doc.
  * `gero repl` needs the opposite for `shell`, and for `!` if it is ever built: the user's own shell, a typed line as a string and the user's environment. That is a separate function in `execx`, `Passthrough`, which is not a method on the allow-listed `Runner`. It is used only by the REPL, takes the user's `$SHELL` and the whole environment, and has no allow list, since the user's own shell is what it runs; this is the policy entry for it ([REPL](REPL.md)).
  * `internal/platform/git/gitcli` and `internal/gero/ghcli` run their binaries through it. `gitcli` is the git client for everything that touches a working tree: clone, fetch, status, branches, worktrees, commits, signing and pushes ([EXECUTION_CONTEXT](EXECUTION_CONTEXT.md)), and the short commit hash, whose length depends on the repository's object count and which go-git cannot reproduce ([BRANCH_TAGS](BRANCH_TAGS.md)). `ghcli` serves `gero doctor` ([DOCTOR](DOCTOR.md)).
* Not adopted: `viper`, logging libraries, and any library that owns the screen (Bubble Tea and its kin; `reeflective/console`). Styling is lipgloss v2 and the line editor is `ergochat/readline`, above ([CLI_FRAMEWORK](CLI_FRAMEWORK.md), [CLI_OUTPUT](CLI_OUTPUT.md)).
